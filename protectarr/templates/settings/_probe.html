Content Probe - advanced, opt-in {% if summaries.probe %}{{ summaries.probe.text }}{% endif %}

{#- Kept out of the disclosure: it is the sentence that tells an operator switching this on that it cannot cause a false removal. -#}

Catches a payload wearing a real .mkv or .mp4 extension by reading the first piece of one file. A file that cannot be read, cannot be recognised, or runs out of budget produces no finding - never a removal.

How this works

Everything else Protectarr does reads the torrent's file list, which is why it costs no bandwidth and answers in seconds. That cannot catch a payload wearing a real .mkv or .mp4 extension, because nothing in the metadata is lying. The probe downloads the first piece of one file - a few MB out of many GB - and checks the bytes really are the format the name claims.

It only runs on torrents the fast checks had nothing to say about, and only on torrents your reaping rules would let Protectarr act on.

A scan that has a fake queued for removal reaps it first and probes on the next pass, so probing never delays a removal the fast checks already decided on.

No mappings, which is correct if Protectarr already sees the downloads at the same path qBittorrent reports. Add one only if the two differ.

How this works

Protectarr has to be able to read the files qBittorrent is writing, so mount the download directory into Protectarr as well. If it lands at the same path qBittorrent reports, you are done and need nothing here.

Add a mapping only when the two see the same folder at different paths: it translates one into the other. Note the path to match is the one qBittorrent reports, which on a NAS is often not the host path - a share at /volume2/Media/torrents may be /Media/torrents to qBittorrent. The Test button prints both paths for a live download, so you can check rather than guess.

Advanced tuning

Reading a piece the torrent already happens to have is free, and always allowed. Fetching one on purpose means briefly raising one file's priority above the torrent's other files and turning on sequential download - always restored afterwards, and restored on the next start if Protectarr is killed mid-probe. Nothing is switched off, so the torrent's size and progress never change. These limits bound what that is allowed to cost.

Uncheck to only ever read what is already downloaded. Everything below only bounds the steered half, so it does nothing while this is off.

Stop steering early when Protectarr sees no progress toward the target file's opening piece for this long, and put the settings back. This watches that one piece, not the file's overall progress: a torrent can be pulling bytes for the file at full speed while the piece we actually need is never requested, which is measured behaviour rather than a hypothetical. Without this the probe would hold the boost for its whole budget while accomplishing nothing.

Steering only influences which piece qBittorrent picks next; it cannot recall one already in flight. On a torrent crawling from one seed the piece may be twenty minutes away, so the budget is better not spent. Fakes are heavily seeded by design - the attacker wants downloads - so the torrents that matter are the ones this works best on.
