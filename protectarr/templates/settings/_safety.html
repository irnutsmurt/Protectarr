How this works

either covers a gap the others leave open. When an application fails a release it drops it from its queue but the torrent can keep downloading in qBittorrent, owned by nobody - arr_tracked will not touch it and the payload finishes anyway. In either mode a tracked torrent is still handed back to its application (which blocklists it and decides about requeueing), and an orphan in an allowed category is deleted from qBittorrent directly.

Handing a download back to its application is always preferred, because that is the path that blocklists the release so the same fake is not grabbed again. Deleting from qBittorrent can only stop this copy.

Ownership & Orphan Handling

How long a previously application-owned download must remain continuously confirmed absent before category fallback may act on it.

How this works

Protectarr remembers which application owned each download. When one disappears from that application's queue it becomes an orphan, and only then can the category fallback act on it.

Confirmed absence means Protectarr successfully read that application's queue and the download was not in it. A queue it could not reach does not count and does not advance the clock - an application that is down or restarting never ages its own downloads into orphans. If the download reappears the clock resets to zero.

A download that has finished is never an orphan either: succeeding also removes it from the queue, which is the application importing it rather than abandoning it.

Advanced tuning

How long past the air or release time to wait before a replacement search is allowed. Web releases often land a little after the broadcast slot. Has no effect unless the replacement search above is on.
